## Critical

### C1. Client upload portal never actually uploads files — FIXED (`f1e7e2b`)
**File:** `src/pages/UploadPortal.tsx` (`handleFiles`, `handleSubmit`)
The public upload page (`/upload/:token`) that clients use to send documents to their CA **simulates** an upload with a `setInterval` progress bar and never writes the file anywhere. `handleSubmit` only updates `document_requests.status = 'uploaded'`. There is no `supabase.storage.from('ca-munim-documents').upload(...)` call. Result: the CA sees the request marked "uploaded," but the actual document does not exist. This defeats the core purpose of the document-collection feature. A private storage bucket `ca-munim-documents` exists but is never written to.

### C2. Anyone (unauthenticated) can read every firm's document requests
**Where:** RLS policy `doc_requests_public_token` on `public.document_requests`
The policy grants `SELECT` to role `public` (includes the anonymous key) with the condition `(upload_token IS NOT NULL)`. That is not scoped to a specific token — it exposes **all** document-request rows across **all firms** (client_id, document_type, due_date, upload_token) to anyone with the public anon key. The upload portal only needs to read the single row matching its token. This is a cross-tenant data leak.
**Fix:** scope the public policy to the exact token being requested (e.g., require `upload_token = <requested token>` via a security-definer RPC or a per-token filter), and prefer a narrow lookup rather than an "is not null" predicate.
**Confirmed fixed, fix shape (2026-07-14, in response to external review):** `20260702130000_upload_request_lookup.sql` — exactly the recommended shape. Adds `public.get_upload_request(p_token text)`, a `SECURITY DEFINER` RPC (`set search_path = ''`) that looks up a single row by `upload_token = p_token`, then drops the old `doc_requests_public_token` policy entirely so `anon` has no direct `SELECT` on the table at all — every read goes through the token-scoped RPC.

### C4. Live cron-trigger secret committed in plaintext to a public repo — FIXED, verified closed 2026-08-26 (originally mis-marked fixed 2026-07-14; the env-var half was never done until now)
**Files:** `supabase/migrations/20260707120000_scheduled_reminders.sql`, `supabase/migrations/20260708060000_recurring_task_cron.sql`
Both migrations inlined the literal `x-cron-secret` value (`ktYNhaQ6lKbNr6fNU8wtimgWX3V744Dg`) used to authorize `pg_cron` calling `send-task-reminders`/`generate-recurring-tasks`. Since `verify_jwt` can't apply to a cron-triggered call (no user session to attach a JWT to — see the original migration's own comment), this shared-secret header was the *only* gate on those functions, and the repo being public meant anyone could read it straight out of the migration file, then call either function directly: real WhatsApp template sends to real client phone numbers on the firm's Meta bill (degrading the number's quality rating), or unbounded task generation. Root cause per the original migration's comment: there's no MCP tool to set Edge Function secrets (Dashboard/CLI only), so the value had to be manually kept in sync between the DB cron job and the function's env var, and inlining it in a migration was the shortcut that made that sync possible — at the cost of committing it.

**Fix:** rotated to a new secret, stored *only* in Supabase Vault (`pgsodium`-backed, already used by the client-credential-vault feature) via `vault.create_secret()`, run by hand against the live project — not committed to a migration, for the same reason the leak happened in the first place. Both `cron.job` rows were repointed (`cron.alter_job`, also run by hand) to build the `x-cron-secret` header from `(select decrypted_secret from vault.decrypted_secrets where name = 'cron_secret')` instead of a literal. `supabase/migrations/20260714210000_rotate_cron_secret_to_vault.sql` captures the *structural* change (the vault-lookup command) so it's reproducible from migrations, but deliberately contains no secret value — a fresh environment rebuilt from migrations alone would need its own `vault.create_secret('cron_secret', ...)` run by hand, same as `CRON_SECRET` already required manual setup per project.
**VERIFIED 2026-08-26 — the env-var step was NEVER completed, so this is still open (and made worse by a second leak).** Live checks against the project: both `cron.job` rows resolve their `x-cron-secret` from `vault.decrypted_secrets` (the DB-side rotation is genuinely done), and the Vault `cron_secret` holds the rotated value, not the old literal. BUT `net._http_response` shows the daily cron getting **`403 Forbidden`** (the function's own line-96 response — `return new Response('Forbidden', { status: 403 })`), most recently on the `2026-08-26 03:00Z` run. That proves the request reaches the secret check and fails it: the function's `CRON_SECRET` env var does NOT equal the Vault value the DB sends — i.e. `supabase secrets set` was never run. Two live consequences: (1) **functional outage** — daily reminders and recurring-task generation have been silently 403ing, not firing; (2) **security hole still open** — the env var was never changed off the old leaked `ktYNhaQ6…`, so the function almost certainly still accepts that public value, meaning any reader of the repo can still trigger the functions. **Second leak, found the same day:** the rotated replacement secret was itself written in plaintext into THIS file (the old `supabase secrets set CRON_SECRET=…` line, now redacted) and committed — so that value is public too. Both known secrets are therefore burned.
**Correct remediation (user must do — I cannot set Edge Function config or handle the live secret):** generate a genuinely FRESH secret (`openssl rand -base64 36`), then set it in BOTH places to the same value — the function env var via `supabase login` + `supabase secrets set CRON_SECRET=<FRESH> --project-ref djzsjkjdvzqxybltikmr`, and the Vault entry via the SQL console (NOT a committed migration): `select vault.update_secret((select id from vault.secrets where name='cron_secret'), '<FRESH>');`. Do not write `<FRESH>` into any tracked file. The moment the env var is set to `<FRESH>`, both public values (`ktYNhaQ6…` and the redacted one) stop being accepted — closing the hole — and the cron starts succeeding again (200), since DB and function now agree.
**Done 2026-08-26:** Vault `cron_secret` verified rotated to a fresh 48-char value (`vault.secrets.updated_at` = 15:28:04Z; equals neither `ktYNhaQ6…` nor the previously-leaked value). User confirmed the Edge Function `CRON_SECRET` env var was set to the same fresh value (function config isn't readable via any API/MCP tool, so this half rests on that confirmation). **Confirmed closed 2026-08-26:** negative test run — `POST generate-recurring-tasks` with the old public `ktYNhaQ6…` header returned **`HTTP/1.1 403 Forbidden`** (the function's line-96 rejection), empirically proving the Edge Function no longer accepts the leaked value. Both public secrets (`ktYNhaQ6…` and the previously-committed replacement) are now dead; the exposure is closed. **Functional note (not a security item):** the daily cron had been 403ing since the DB was repointed to Vault (reminders/recurring-task generation not firing in the interim); the first 03:00Z run after this rotation should return 200 now that DB (Vault) and function env var agree — worth a glance to confirm the jobs resumed, but the security hole is closed regardless.
**Process lesson (why this sat open ~6 weeks):** the original fix depended on a manual, off-repo `supabase secrets set` that silently never happened, and nothing surfaced the resulting daily 403s — the entry was marked FIXED on the DB-side change alone. Guardrails worth adding: (1) an alert on repeated cron 403s (a silently-dead scheduler is its own incident), and (2) treat any "user must run X outside the repo" handoff as a tracked, verified to-do, not a note in this file. Also: the replacement secret was itself committed here in plaintext (now redacted) — never write a live secret into a tracked file, even a docs one.
**Deliberately not done:** git history rewrite to purge the old literal from the two original migration files. Per the same reasoning as L2 below — the value is dead the moment the env var is updated, rotation alone neutralizes the leak, and rewriting a public repo's history has its own risks. Left the original two migration files untouched (accurate historical record); the new migration supersedes their cron-job effect when replayed in order.

### C5. Record Payment does not actually record the payment — invoice status and payments table are both untouched — FIXED (2026-07-18)
**Files:** `src/components/billing/RecordPaymentModal.tsx`, `src/pages/Billing.tsx`, `src/hooks/useBilling.ts` (`recordPayment` — fully implemented, never called)
Found while checking Billing for the same mutation-error architecture issue as M19 (Tasks), and it turned out to be much worse: `RecordPaymentModal.handleSubmit` validates the amount/mode client-side, then does nothing but show a success toast (`"Full payment of ₹X recorded — Invoice marked as Paid"` or the partial-payment equivalent) and close the modal. It never calls `useBilling`'s `recordPayment(invoiceId, clientId, amount, mode, ...)` — that function is fully implemented (inserts a `payments` row, recomputes `paid`/`partially_paid` status, updates the invoice) and correctly exported from the hook, but nothing wires it to this modal: `Billing.tsx` renders `<RecordPaymentModal open={...} onOpenChange={...} invoice={paymentInvoice} />` with no callback prop at all, and the modal component doesn't import or use `useBilling` itself. This is the same bug class as the already-documented C1 (upload portal never uploads) and the original, now-fixed L1 (fake Razorpay checkout) — a feature that fully simulates success with no backing write.
Reproduced live end-to-end: created a real invoice (`INV-202627-0018`, `total: 1180`), opened Record Payment, entered the full amount (₹1,180) and a payment mode (UPI), submitted — got the exact "Full payment of ₹1,180 recorded — Invoice marked as Paid" toast, dialog closed normally, no error anywhere. Then queried the live DB directly: the invoice's `status` was still `draft` (never became `paid`), and `select count(*) from payments where invoice_id = '...'` returned `0` — no payment record exists at all. Every dependent figure — Fees Dashboard (already flagged inconsistent by H3), the client profile's Pending Fees, Reports' Receivables Aging, the Dashboard metric card — is silently wrong for every invoice a CA believes they've recorded a payment against, because none of those payments are real.
**Fix:** wire `RecordPaymentModal` to actually call `recordPayment` — either pass it (or a wrapping callback) down as a prop from `Billing.tsx` the same way `CreateInvoiceModal` receives `onCreated={loadInvoices}`, or have the modal accept `useBilling`'s `recordPayment` directly. The modal's existing client-side validation (amount range, mode required) is fine and should stay — it's the actual persistence call that's missing entirely.
**Fixed:** `RecordPaymentModal` now calls `useBilling().recordPayment(...)` directly, awaits it, only shows the success toast and closes on a genuine success, and calls a new `onRecorded` prop (`Billing.tsx` passes `loadInvoices`, matching `CreateInvoiceModal`'s `onCreated` pattern) so the invoice list refreshes with the real status. Submit button now disables mid-request instead of being instantly clickable again. Found and fixed one more silently-discarded field in the same modal while wiring this up (M8/M14/M18 pattern): the "Payment Date" input had state but was never read anywhere — `recordPayment` always inserted `payment_date` as today regardless of what the user picked. Added an optional `paymentDate` parameter to `recordPayment` (defaults to today if omitted, so no other behavior changes) and passed the modal's actual selected date through.
**Verified:** the QA agent's `19-billing-record-payment-integrity.spec.ts` (which reproduced this bug end-to-end, including a page reload to bypass client-side optimistic state) was flipped to assert the fixed behavior and passes live against the real dev server + Supabase project. `npx tsc --noEmit` clean.

### C7. `message_templates` cross-tenant write via duplicate/overlapping RLS policies — FIXED (2026-07-23)
**File:** `supabase/migrations/20260604123000_add_message_templates_rls_policies.sql`, fixed by `supabase/migrations/20260723180000_fix_message_templates_rls_bypass.sql`
Found by a background security-audit agent, launched after the user shared a checklist of common vibe-coded-app vulnerabilities to check for (secrets in client bundle, missing RLS, auth-vs-authorization/IDOR, exposed debug routes, CORS wildcard, plus a broader OWASP Top 10 sweep — four parallel audits total). The RLS-coverage pass found this table had two overlapping sets of policies: the correct, later-added `templates_all` (`firm_id = get_my_firm_id()`, covers all of SELECT/INSERT/UPDATE/DELETE) alongside four older policies from the original migration scoped only by `auth.uid() = user_id` — no `firm_id` check at all — that were never dropped when `templates_all` was added. Postgres ORs multiple `PERMISSIVE` policies for the same command together, so a row only needs to satisfy **one** of them: the legacy `INSERT` policy's `WITH CHECK` never looked at `firm_id`, so any authenticated user could insert a `message_templates` row with an arbitrary `firm_id` (any other firm's) as long as `user_id` matched their own `auth.uid()`. Same "duplicate/overlapping RLS policy" bug class as the already-fixed M6 (`firms`), just never caught for this table.
**Exploited live to confirm** (2026-07-23): signed in as a real staff member of one firm (`ca.munim.test1`), inserted a template with a different real firm's `firm_id` (`TestFirm`) — succeeded, returning the row with the other firm's `firm_id` set. Impact: any authenticated user in any firm could inject arbitrary WhatsApp message-template content into another firm's template list, potentially sendable to that firm's real clients. Not a read leak (the correct `templates_all` policy still gated SELECT to the caller's own firm), but a real tenant-isolation write bypass. Test row deleted immediately after confirming.
**Fixed:** dropped the four legacy `user_id`-only policies (`Users can delete/insert/select/update their own templates`). `templates_all` already correctly covers all CRUD via its single `ALL` policy — for a `FOR ALL` policy with no explicit `WITH CHECK`, Postgres uses the `USING` expression (`firm_id = get_my_firm_id()`) as the `WITH CHECK` too, so no replacement policy was needed, only removing the bypass.
**Verified:** re-ran the exact live exploit attempt post-fix — now correctly rejected (`42501: new row violates row-level security policy for table "message_templates"`). Separately verified a legitimate same-firm insert/select/delete round-trip (the exact path `MessageTemplates.tsx`'s M16 fix relies on) still works correctly post-fix. `select * from pg_policies where tablename='message_templates'` now shows only the one correct policy.
**Direct fallout found and fixed in the same pass — `saveMessageTemplateToSupabase` never set `firm_id`:** closing the RLS hole immediately broke real functionality that had been silently relying on it. `src/data/WhatsappApi.ts`'s `saveMessageTemplateToSupabase` (used by every template save, including the M16 duplicate fix) never included `firm_id` in its insert payload — only the legacy, now-removed `auth.uid() = user_id` policy let those inserts through at all, always landing with `firm_id: NULL`. Found by testing the new mobile Home screen's live "Nudge on WhatsApp" button (see the Product Direction / mobile redesign entry below): the client-phone lookup succeeded but the template lookup came back empty — `templates_all` (`firm_id = get_my_firm_id()`) never matches `NULL`, so once C7 closed the bypass, every template a firm had ever saved through the app's own UI — including all 4 real production WhatsApp templates registered with Meta for H5/H7 — became invisible to that firm, breaking `sendQuickReminder`'s template lookup everywhere it's used (C6, M21's task-reminder path indirectly, the new mobile Home nudge button). Confirmed via a direct query all 5 affected rows (`Documents Pending`, `GST Filing Reminder`, `Hello World`, `Invoice Payment Due`, `ITR Filing Reminder`) belonged to the same firm/user (`staff.auth_user_id → firm_id` traced), not a cross-firm mixup.
**Fixed:** `supabase/migrations/20260723190000_backfill_message_templates_firm_id.sql` backfills the 5 orphaned rows to their real owning firm. `saveMessageTemplateToSupabase` now looks up `staff.firm_id` (same pattern used everywhere else in the codebase) and always includes it in the insert/upsert payload, so this can't recur for any firm going forward.
**Verified:** re-signed in and confirmed all 5 templates are visible again (`fetchMessageTemplatesFromSupabase` returns all 5), confirmed a fresh insert via the fixed function now sets `firm_id` correctly matching the signed-in user's real firm, confirmed the "GST Filing Reminder" template is now findable by `sendQuickReminder`'s partial-name lookup again. `npx tsc --noEmit` clean, full unit suite (118/118) passing.
**The other three audit passes (secrets/CORS, authorization/IDOR/debug-routes, broader OWASP sweep) found no new confirmed issues** — prior fixes (C2, C3, C4, M2, M5, M6, M10) were independently re-verified and hold up. Two minor items surfaced, not urgent: (1) `npm audit` findings — **applied 2026-07-27**: `npm audit fix` (non-force) resolved `fast-uri`, `form-data`, `js-yaml`, and `postcss` (28 → 17 vulnerabilities), and `vite` was bumped 7.3.5 → 7.3.6 within its existing `^7.3.5` range. Three remain, all requiring a `--force` major-version bump to actually resolve (not applied — same reasoning as never force-bumping `react-router-dom` mid-session: these are central dependencies and a major bump is a bigger, riskier change warranting its own explicit pass): `brace-expansion` (HIGH ReDoS, transitive dev-only via `glob`/`eslint`, not shipped to the browser — force-fixing would bump `eslint` to a breaking v10), `esbuild` (HIGH, arbitrary file read on the Windows dev server — transitively pinned by `vite@7.x`'s own dependency range; even `vite@7.3.6` still resolves a vulnerable `esbuild@0.27.7`, the actual fix needs `vite@8.x`), and `react-router`/`react-router-dom` (MODERATE, SSR-hydration/open-redirect CVE — this is a client-only SPA so the SSR variant doesn't apply; the vulnerable range is `6.0.0–7.17.0`, i.e. *all* of v6, so no non-breaking fix exists within the current `^6.30.1` — only a v7 major bump, itself a significant migration). (2) the debug-* edge functions `debug-test-resend-email` and `debug-list-templates` are confirmed inert `410 Gone` stubs (same decommission pattern as H5's `debug-whatsapp-templates`) but weren't previously logged here alongside it — now noted.

### H2. `bootstrapMissingRecords` firm insert is blocked by RLS and fails silently — FIXED
**File:** `src/App.tsx`

## Architecture & Product Roadmap (Fable architect/PM review, 2026-07-06)

A second-pass review covering architecture and product gaps, not just correctness bugs. Ranked priority order below is the reviewer's combined recommendation, adjusted for what's since shipped in this repo (Razorpay is live — L1; direct Meta WhatsApp send/receive is live — H5/webhook work, so "BSP integration" below is already done, leaving the scheduler as the actual gap).

### P1. Fix the three wrong statutory values — quick, no schema change
The GSTR-4 due date, GSTR-3B/GSTR-1 late fee caps, and GSTR-9 late fee — see H6. Do this first; it's the fastest fix and the one most likely to burn credibility with a CA reviewer if left as-is.

### P2. Move compliance rules out of the JS bundle into `compliance_rules`
See H6's correction above — the table and partial seed data already exist. Scope: complete the seed data (missing filing types, turnover-slabbed `late_fee_rule`), build one resolver function, delete `dueDateRules`/`penaltyRules.ts`/the hardcoded parts of `indianTaxUtils.ts`.

### P3. No scheduler — the core "never miss a deadline" promise is not automated
**Certain, and more fundamental than any BSP gap.** Nothing runs when no one has the app open — no cron, no scheduled Edge Function, no queue. "Send Reminder" requires a human to click it every time. Fix: one Supabase-scheduled Edge Function (`pg_cron` + `pg_net`, calling the function via HTTP on a schedule) that scans tasks due in N days and queues/sends WhatsApp reminders automatically. Without this, the product's core pitch is aspirational, not real.

### P4. Recurrence engine driven by `clients.services_subscribed`
**Biggest product disconnect.** `AddClientModal` collects "Services Subscribed" (ITR, GST monthly/quarterly, TDS...) into `clients.services_subscribed` (jsonb) and nothing reads it to generate tasks. Task creation today is manual or via the bulk generator (a batch workaround for a missing recurrence engine). Should instead auto-generate recurring tasks (with correct due dates once P2 lands) for as long as a service is subscribed. This is the specific gap a Jamku reviewer flagged as missing there — an open competitive flank.

### P5. Excel importer for clients
Every prospect firm has 100–300 existing clients in Excel or Jamku today. No importer means hours of manual re-entry before the product shows any value — likely the single biggest trial-drop-off point. Highest-leverage onboarding feature buildable.
